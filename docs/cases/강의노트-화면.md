### 2026-08-06 · 절을 나눌 때는 래퍼 구조부터 본다

2026-08-06 인공지능기초 개정에서 이 구별을 놓쳐 **두 번 깨뜨렸다.**

**① 래퍼 하나에 `<hr>`로 나뉜 구조** — 래퍼를 닫았다가 새 절에서 다시 연다.

```html
<section id="intro">
    <div class="section-card space-y-8">     <!-- 이 래퍼를 -->
        <div>…첫 블록…</div>
        <hr class="border-slate-100">         <!-- 여기서 자르고 -->
        <div>…둘째 블록…</div>
    </div>
</section>
<!-- ↓ 나눈 뒤 -->
<section id="intro">
    <div class="section-card space-y-8">
        <div>…첫 블록…</div>
    </div>                                    <!-- 닫고 -->
    …스스로 확인 밴드…
</section>
<section id="integrate">
    …h2 · 부제…
    <div class="section-card space-y-8">      <!-- 다시 연다 -->
        <div>…둘째 블록…</div>
    </div>
</section>
```

**② 블록이 각자 `section-card`인 형제 구조** — 그냥 자르면 된다.

**정규식으로 `<div>` 스택을 세지 마라.** 이 저장소에는 여는 태그가 여러 줄에 걸친 `<div>`가
흔하다(「스스로 확인」 밴드가 대표적). `<div[^>]*>`로는 그 태그가 안 세어져 스택이 어긋난다.

```html
<div class="bg-gradient-to-r from-sky-50 to-slate-50 border border-sky-200
            border-l-4 border-l-sky-500 rounded-2xl px-6 py-5
            flex flex-col sm:flex-row gap-4 items-start sm:items-center">
```

### 2026-08-05 · `<sup>` `<sub>` 금지

2026-08-05 데이터과학 `3-2-2`에서 7곳, `3-1-1`에서 4곳 발견. 브라우저 실측으로만 잡혔다.
브라우저가 `<sup>` `<sub>`를 `0.83em`으로 줄여 `text-base` 문단 안에서 12~13.5px가 되는데,
**소스에 `text-sm`이 없으므로 검사기는 통과시킨다.**

```html
<p>오차<sup>2</sup></p>        <!-- X : 12px로 렌더링된다 -->
<p>오차&sup2;</p>              <!-- O : 본문 크기 그대로인 위첨자 글자 -->

<p>y = a<sub>1</sub>x<sub>1</sub> + …</p>          <!-- X -->
<p>독립 변수 하나마다 계수가 하나씩 붙는다</p>        <!-- O : 문장으로 푼다 -->
```

제곱은 `&sup2;`(`3-1-2`의 `r&sup2;`가 선례). 아래첨자는 대응 문자가 마땅치 않아 **문장으로 푼다.**

### 2026-08-04 · 목록은 `list-outside`

`list-inside`는 마커가 콘텐츠 박스 안에 들어가 **줄바꿈된 둘째 줄이 번호 아래 맨 왼쪽으로 붙는다.**
좁은 화면일수록 줄바꿈이 잦아 더 자주 깨진다. `list-outside`는 마커를 콘텐츠 박스 밖에 그리므로
`pl-5` 이상이 없으면 마커가 잘린다.

원문자(`①②③`)를 쓰지 않는 이유 — 보조기기가 읽는 방식이 제각각이고, 항목을 넣거나 빼면
손으로 다시 매겨야 하며, 글꼴 폴백 시 두부(□)로 깨진다.
(2026-08-04 전 과목 24개 파일 일괄 교정 완료)

### 2026-09-25 · 코드를 HTML 안에 두지 않는 이유

프로그래밍 44개 파일의 코드블록 **276개**(평균 8.3줄)를 조사한 결과다.
수동 하이라이팅 span은 이미 0개라 **Prism 탓이 아니었다.** 진짜 원인은 둘이었다.

1. **이스케이프 불일치** — `&lt;` 138건, `&gt;` 103건. 그중 **5개 블록은 같은 블록 안에서**
   주석의 `<`는 raw, 코드의 `<`는 `&lt;`였다. 브라우저에서 똑같이 보이므로
   **복사해서 고치는 것이 불가능했다.**
2. **`onclick="copyCode('code-98')"`** — id 95개가 파일을 넘어 중복.

실파일로 빼면 편집기가 문법을 알고, 검사기가 구문 오류를 잡고,
학생이 내려받는 파일과 화면에 뜨는 코드가 같아진다.

**Prism 진입점을 빠뜨리면 조용히 흐려진다**(2026-09-25). 빌드는 코드 본문만 넣고 배경과 색은
Prism이 붙이므로, 진입점이 없으면 바탕 없는 흐린 글자로 나가는데 화면으로는 빠진 줄 모른다.
그래서 `check -- code`가 코드 블록이 있는 페이지의 진입점을 본다.

**코드 파일 이름 앞에 강의노트를 적는 까닭** — 한 `code/` 폴더에 여러 차시의 코드가 쌓인다.
이름만 보고 어느 차시 것인지 알 수 있어야 하고, 파일 목록이 강의노트 순서대로 정렬되어야 한다.
검사는 공백만 본다. 앞머리까지 세우면 실습처럼 이름을 줄여 붙인 맞는 이름이 걸려서 뺐다.

### 2026-08-11 · SVG 글자 크기 — 바닥만 있고 천장이 없었다

`min-width`(모바일에서 줄어들지 않게 하는 바닥)는 챙기면서 `max-width`(데스크톱에서
커지지 않게 하는 천장)는 빠뜨리기 쉽다. 375px만 보고 고치기 때문이다.

2026-08-11 감사 도구를 고치기 전에는 **24건이 걸렸는데 실제 결함은 1건**이었다.
도구가 `style`의 `max-width`만 보느라 아래를 전부 결함으로 세었다.

| 이미 묶여 있던 것 | 왜 괜찮은가 |
|---|---|
| `class="… max-w-2xl mx-auto"` | Tailwind 클래스도 천장이다. 정규식 끝의 `\b`가 `max-w-[200px]`의 `]` 뒤에서 서지 않아 통째로 놓쳤다 |
| `width="100" height="70"` | 값이 박혀 있으면 아예 늘어나지 않는다 |
| `style="max-height:260px"` | 높이가 묶이면 `preserveAspectRatio` 때문에 배율도 함께 묶인다 |
| 높이 고정 부모 + `class="h-full"` | 같은 이유 |

**가운데 정렬도 폭 천장이 있을 때만 문제가 된다.** 높이로 묶인 그림은 남는 자리가
좌우로 생기는데 `preserveAspectRatio` 기본값(`xMidYMid`)이 이미 가운데 놓는다.
폭 천장이 걸려 SVG **요소 자체가** 부모보다 좁아질 때만 왼쪽에 붙는다.

**감사 도구가 시끄러우면 도구부터 고친다.** 24건을 그대로 믿고 고쳤다면
이미 멀쩡한 23곳에 쓸데없는 속성을 붙이고, 진짜 한 건은 그 속에 묻혔을 것이다.

**천장이 왜 필요한가** — `class="w-full"`인 SVG는 부모 폭에 맞춰 늘어나고 `<text font-size>`도
그 비율로 함께 커진다. 천장이 없으면 데스크톱·빔프로젝터에서 도해의 글자만 과하게 커진다.
천장을 viewBox 폭에 가깝게 잡는 것은 배율이 1에 가까워야 의도한 크기로 그려지기 때문이다.

**바닥도 같은 셈이다.** `viewBox="0 0 560 200"`인 그림을 520px로 그리면 `font-size="14"`가
**13px**로 앉는다. `min-width`와 `max-width`를 같은 값으로 묶으면 데스크톱에서도 같은 크기이므로
좁은 화면만의 문제가 아니다. 모자랄 때 `font-size`를 올리지 않는 까닭은 [수정 레시피](../수정-레시피.md)의
「SVG 글자가 작다고 나올 때」에 있다. 나란히 놓는 짝을 480으로 묶는 까닭 — 2열 칸에 넣은 576짜리는
데스크톱에서도 가로로 밀린다.

**정적 검사로는 안 보이는 것이 있다**(2026-09-25). 제목과 첫 표지가 포개지는 것, 좁은 칸에 눌려
글자가 줄어드는 것은 `font-size` 숫자만 보아서는 모른다. 그래서 `audit -- svg`가 진짜 브라우저로
글자를 잰다. 전체를 재면 1~2분인데 SVG를 고칠 때만 뜻이 있어 `ci`에 넣지 않았고, 그러니
**고친 사람이 돌리지 않으면 아무도 잡지 않는다.**

→ 규칙: docs/강의노트-작성-규칙.md 「SVG」

### 2026-09-26 · 본문에 남는 폭

375px에서 «글이 놓이는 폭»은 바깥 것들을 다 빼고 남은 값이다. 이 값이 200px 아래로
내려가면 한 줄에 한국어 열두 자가 채 안 들어가 **읽기가 아니라 해독이 된다.**

| 무엇이 | 먹는 폭 |
|---|---|
| `<main>` 좌우 여백 | 32 |
| `.section-card` 좌우 여백 | 40 |
| 안쪽 카드 `p-4` | 32 |
| **아이콘을 왼쪽에 세운 가로 배치** (`w-10` + `gap-4`) | **56** |

여백은 데스크톱에서 보기 좋으라고 준 값이라 모바일에서 눈에 띄지 않고, **겹칠수록 본문 칸이 토막 난다.**
그래서 `.section-card`와 `<main>`의 여백을 좁은 화면에서 줄였고, 아이콘은 좁을 때만 위로 쌓는다
(sm 640px 위로는 원래 모습 그대로다).

**`items-*`를 함께 고치는 까닭** — 가로일 때 `items-start`는 «위로 붙임»이지만, 세로로 쌓이면
**«내용 폭에 맞춤»**이 된다. 그러면 안에 든 넓은 표(`table-prose`는 `min-width: 32rem`)가 칸을 밀어내
**페이지가 통째로 가로로 넘친다.** 좁을 때는 `items-stretch`라야 칸이 화면 폭을 채운다.
검사는 폭을 스스로 못박은 자식(`w-full` 등)을 뺀다 — 줄어들지 않기 때문이다.

**한 줄만 고치지 않는 까닭** — 다섯 단계짜리 목록에서 글이 긴 5번만 쌓이면 더 어긋나 보인다.
`audit -- narrow`가 `ci`에 없는 까닭 — 추정이라 글을 조금 늘렸다는 이유로 빨간불이 되면 안 된다.
고친 이야기는 [수정 레시피](../수정-레시피.md)의 「모바일에서 글이 한 줄에 서너 낱말씩만 들어갈 때」.

→ 규칙: docs/강의노트-작성-규칙.md 「화면」

### 2026-09-26 · 도식의 이름은 그림 안에

차트 예시는 값이 아니라 모양을 보이는 그림이라 자리와 이름이 어긋날 일이 없다. 도식은 상자가
여럿이면 **어느 상자가 무엇인지 자리로만은 알 수 없다.** 밖의 위치 해독표는 결함을 알아보는 가장
확실한 냄새이고, 이름을 안으로 옮긴 뒤 해독표를 남기면 같은 말이 두 번 나온다. 사례는 [오개념 판례](오개념.md) 「무주석 첫 등장 · 정의 흔들림」의
「도해 전수 점검」 항목.

→ 규칙: docs/강의노트-작성-규칙.md 「SVG」

### 2026-08-11 · HTML 양식 규칙의 근거

- **hero 배지에 단원 · 차시 번호를 넣지 않는 까닭** — 교육과정이 바뀌어 파일 번호를 두 번 다시
  매기는 동안 인공지능기초 대부분의 배지가 파일과 어긋났고, 서로 다른 파일이 같은 배지를
  달기도 했다. 위치는 목록 · 파일 이름 · nav가 이미 알려 준다. 푸터에 소절 제목 · 단원 번호 ·
  연도를 넣지 않는 것도 같은 까닭이다.
- **제목을 파일 이름 · `<title>` · `<h1>` 세 곳에서 맞추는 까닭** — 파일 이름을 바꿀 때 `<title>`과
  nav만 고치고 hero를 놓쳐 인공지능기초 절반 넘게 옛 제목을 달았고, 두 파일이 목록에서
  같은 파일처럼 보였다. nav는 폭이 좁아 줄여 적으므로 대조하지 않는다(2026-08-11 사용자 확정).
  시뮬레이터는 `<h1>`에 교실용 후킹 문구를 두던 것을 hero 부제로 내렸다 — 예외를 만들지 않고 후킹도 지키는 길이었다.
- **핵심 정리를 넓은 화면에서 2열로 두는 까닭** — 3열 · 4열이면 흔한 노트북 폭에서 카드가 좁아져
  항목마다 줄이 바뀐다. 2열이면 한 줄에 들어가 빔프로젝터에서 읽기 쉽다. 짧은 항목의 3열 카드는 그대로 둔다.
- **푸터를 밝고 얇게 두는 까닭** — 검정 블록은 페이지 배경(`#f8fafc`)과 따로 놀았다(사용자 표현
  「너무 다크해서 멋없어」). 아이콘 박스를 `w-11 h-11`로 고정하면 44px 터치 타깃이 되고 위아래 여백이
  맞는다. 아이콘만 두므로 `title`과 `aria-label`이 없으면 스크린리더가 읽을 것이 없다.
- **`<details>`로 접는 것을 어렵거나 심화인 내용에 한정하는 까닭** — 접힌 것은 혼자 읽는 학생이
  그냥 지나친다. 데이터과학 1-1-1에서 용어 뜻풀이 · 배경 설명 넷을 접었다가 모두 되돌렸다(2026-08-04).
- **밝은 그러데이션을 쓰지 않는 까닭** — `bg-gradient-*`는 `background-image`만 만들고
  `background-color`는 투명으로 남긴다. 다크 모드 확장이 배경색만 바꾸고 글자만 밝게 돌려 대비가
  무너졌다. 같은 뿌리가 인쇄에서도 터졌다 — 종이에는 그림 배경이 그려지지 않아 짙은 hero의 흰 글자가
  흰 바탕에 앉았다. 그래서 그림 배경에는 단색 배경색을 함께 깐다. 다크 모드를 공식 지원하지는 않는다
  (2026-08-22 사용자 확정) — 확장에서 읽을 수 없게 되는 것만 고친다.
- **교육과정 밖 내용을 지우지 않고 「참고」로 낮추는 까닭** — 심화 · 보충 자료로 쓸 수 있다.
  호박색 배너 · 절 제목의 회색 `참고` 칩 · 학습 목표의 「(참고 자료)」 셋을 함께 단다.
- **템플릿에 없는 요소를 묻고 넣는 까닭** — 한 편에 넣은 틀이 수십 편에 복제된다. h2에 원문자 번호를
  붙이고 학습 목표 배너에 없던 행을 만든 초안이 반려된 적이 있다(2026-08-04).
- **배치에 기대 위치를 말하지 않는 까닭** — 「오른쪽의 트리」는 375px에서 세로로 쌓이면 틀린 말이 된다.
  hover로만 드러나는 값은 터치 기기에서 영영 안 보인다.

→ 규칙: docs/강의노트-작성-규칙.md 「화면」

### 2026-09-27 · nav 배치와 학습 목표 수에는 따로 까닭이 없음

nav 항목이 여덟을 넘을 때의 배치와 학습 목표를 2~3개로 두는 것은 까닭을 따로 적어 두지 않았다. 사용자는 그렇게 하는 것이
자연스러워서라고 했다 — 코드 소유자의 결정으로 둔다.
